# 第一部分 · 贪吃蛇与 AI 寻路

## 1.1 游戏循环：为什么用 `setInterval` 而不是 `requestAnimationFrame`

贪吃蛇是**回合制**的：蛇每隔固定时间走一格。所以我需要的是"每 150ms 触发一次逻辑"，
而不是"每帧画一次"。

- `setInterval(fn, 150)`：固定间隔调用，正好对应"蛇走一格"。
- `requestAnimationFrame`：跟随显示器刷新率（通常 60fps，即 16.7ms 一次），适合连续动画。

**⚠️ 我踩过的坑**：`setInterval` 返回一个句柄，**必须用 `clearInterval` 清掉**，否则
重开一局会出现两个定时器同时跑，蛇速直接翻倍。我在 `startGameLoop()` 里先清一次旧句柄：

```js
if (gameLoop) { clearInterval(gameLoop); gameLoop = null; }
gameLoop = setInterval(tick, intervalMs());
```

定时器句柄置 `null` 也是必要的，否则 `if (gameLoop)` 判断会拿到一个已经失效的旧 ID。

**速度滑条怎么换算**：`intervalMs() = 680 - slider * 20`，滑条 17→33 对应 340ms→20ms，
即约 3 步/秒到 50 步/秒。滑条 `input` 事件里如果游戏正在跑，要**重建定时器**才能立即生效。

## 1.2 蛇的移动：为什么不会"反向自杀"

蛇的数据结构是一个坐标数组，**第 0 个是头**：

```js
snake = [{x:10,y:10}, {x:9,y:10}, {x:8,y:10}]   // 头在右边，朝右走
```

移动的本质是"**头部增加一格，尾部减少一格**"：

```js
const newHead = 按方向算出新头坐标;
let newSnake = [newHead, ...snake];     // 头插进去
if (吃到食物) { /* 不删尾 → 变长 */ }
else { newSnake.pop(); /* 删尾 → 长度不变 */ }
```

**⚠️ 关键知识点：为什么不能用 `direction`，要用 `nextDirection`。**

用户可能在一次移动的间隔内连按两次方向键（比如蛇朝右时快速按"上"再按"左"）。
如果直接改 `direction`，就会出现"朝右 → 朝上 → 朝左"在**同一帧内**生效，蛇瞬间掉头撞进自己脖子。
所以我用两个变量：`nextDirection` 记录玩家的输入，`direction` 只在真正移动时更新，
并且**移动前检查 newDirection 是否与当前方向相反，相反就忽略**：

```js
const opposite = { up:'down', down:'up', left:'right', right:'left' };
if (opposite[nextDirection] !== direction) direction = nextDirection;
```

**另一个细节：判断"撞自己"时要排除尾巴。** 因为蛇移动时尾巴那一格**会让出来**，
所以头移到"当前尾巴所在格"是合法的。我的做法是判断身体时用 `snake.slice(0, len-1)`，
只排除到倒数第二节；如果这一步吃到食物（尾巴不动），则必须检查到最后一节。

## 1.3 食物生成：为什么不能"随机试 N 次"

原版写法是：随机取坐标，如果落在蛇身上就重试，最多试 1000 次。问题是蛇很长时
命中空格的随机概率下降，重试次数上升，**最坏情况可能 1000 次都失败**，然后代码把食物
硬塞到 `(0,0)`——如果蛇正好占了那里，就出现"食物长在蛇身上"的视觉 bug。

改进版**先枚举所有空格，再均匀随机取一个**：

```js
const occupied = new Set(snake.map(s => s.x + ',' + s.y));
const free = [];
for (let y=0; y<N; y++) for (let x=0; x<N; x++)
    if (!occupied.has(x+','+y)) free.push({x, y});
food = free[Math.floor(rng() * free.length)];
```

蛇长最多 400、棋盘 400 格，枚举的代价可以忽略，但**行为变成确定的**（蛇满盘时自然处理，
不需要"硬塞"这种兜底）。

## 1.4 为什么原来的贪心 AI 会死：问题的本质

原版 AI 的规则是：

1. 比较食物相对蛇头的水平/垂直距离，哪个方向"更接近"就优先走哪个；
2. 逐个检查候选方向是否撞墙、撞自己，不安全就换下一个；
3. 都不安全就保持原方向。

**这个策略缺少一个东西：它只看"眼前这一步能不能走"，不看"走完之后整个局面还活不活得下去"。**

具体会死在两种局面：

**局面一：把自己关进小房间。** 蛇沿墙走时，如果 AI 为了接近食物而选择"贴着墙继续绕"，
蛇身会逐渐把棋盘切出一个封闭的小区域，而食物在区域外面。此时每一步都"安全"，
但**整个区域已经出不去了**，最后只能在里面绕到撞自己。

**局面二：长度增加后的空间不足。** 蛇越长，可活动空间越少。贪心策略不知道"现在吃的这口
会让身体变长，从而把空间压到不够转身"，于是吃着吃着就盘死了。

**实测数据**（`audit/snake_ai_test.js`，300 局固定随机种子）：

| 策略 | 平均吃到 | 达到 15 个的局数 | 最长/最短 | 死因分布 |
|---|---|---|---|---|
| 朴素贪心 | 29.9 个 | 291/300 = **97.0%** | 60 / 7 | 撞自己 294，撞墙 6 |
| BFS 智能 | 65.6 个 | 299/300 = **99.7%** | 102 / 14 | 撞自己 281，撞墙 12 |

**"零人工操作"专项验证**（`python verify_autoplay.py`）：500 局全程只调 `step()`、
一次都不调 `setDirection()`，即完全模拟"人不再碰任何按键"——**500/500 局都达到 15 个，
平均 66.5 个，最差 16 个**。

> 这两组数字的关系值得说明：300 局那组（299/300）里包含一次只吃到 14 个的失败，
> 说明**这是概率事件而不是"必然通过"**，统计样本越大越接近真实成功率。
> 所以准确的结论是"300 局里 299 局、500 局零输入全过"，而不是"绝对没问题"。

**⚠️ 注意 96%+ 的死因都是"撞到自己"**，不是撞墙。这个数字很说明问题：
**AI 不是不会走路，是不会"防自己"**。

## 1.5 改进版 AI 的三层结构

### 第一层：BFS 广度优先搜索求最短路径

**为什么用 BFS 而不是 DFS？**

- **BFS（广度优先）**：像水波纹一样一圈一圈向外扩，**第一次到达目标时走过的步数一定是最少的**。
- **DFS（深度优先）**：一条路走到黑再回头，找到的路径可能绕很远，不保证最短。

在网格里每步代价都是 1，"最短"就等于"最快吃到食物"，所以 BFS 是正确选择。

**实现要点（⚠️ 这里有过一个真 bug）**：

```js
function bfs(start, goal, blocked) {
    const prev = new Map();          // 记录每个格子是从哪来的，用来最后倒推路径
    prev.set(key(start), null);
    const queue = [start];
    let head = 0;                    // 用索引当队头，避免 shift() 的 O(n) 开销
    while (head < queue.length) {
        const cur = queue[head++];
        for (每个方向 d) {
            const nx = cur.x + DIRS[d].x, ny = cur.y + DIRS[d].y;
            if (越界) continue;
            if (prev.has(key)) continue;                    // 访问过就跳过
            if (k !== goalKey && blocked.has(k)) continue;  // ⚠️ 终点永远可通行
            prev.set(k, cur);
            if (k === goalKey) { /* 倒推路径并返回 */ }
            queue.push(...);
        }
    }
    return null;                     // 搜不到，说明食物被身体围住了
}
```

**⚠️ 那个 bug 就是 `k !== goalKey` 这个例外**。我一开始把"终点"也当成障碍，
结果当食物正好落在"会被身体包住的格子"或者食物与蛇尾重合的场景时，BFS 搜不到路径，
AI 就白白进入了保命模式。**起点和终点必须永远可通行，障碍集合只约束中间格。**

**为什么用 `Map` 而不是普通对象**：键是 `"x,y"` 字符串，Map 的增删查更直观，
而且不会和 `Object.prototype` 上的属性名冲突。

### 第二层：安全性校验 —— 两个"不变量"

这一步是**整个改进的核心**：在决定走哪一步之前，先模拟走完这步之后的局面，
检查蛇是否满足两个条件。

**不变量一：头必须还能追到自己的尾巴。**

这是贪吃蛇AI里最经典的一个判据。直觉是这样的：

> 如果蛇头能够到达蛇尾，那么蛇就"有退路"——它可以一直沿着这条路径走，
> 而尾巴也在同步向前移动，所以这条路径**永远存在**，蛇至少不会立刻把自己关死。
> 反过来说，如果**头连自己的尾巴都够不着了**，说明蛇身已经把空间切断了，
> 蛇被关在一个小区域里，迟早撞死。

实现上就是"把蛇尾当成目标，跑一次 BFS"：

```js
const blocked = bodyKeys(newSnake, true);   // 身体全部当障碍（最后一节先排除）
blocked.delete(key(tailNew));               // 但尾巴那一格要放行，因为它马上会让出来
if (bfs(headNew, tailNew, blocked) === null) return false;   // 够不到尾巴 → 这步不安全
```

**不变量二：剩余活动空间不能太小。**

只有不变量一还不够：头能碰到尾巴，不代表空间够用。所以再做一次**洪水填充**
（从蛇头出发，数一数能到达多少个空格），要求：

```js
const space = reachableCount(headNew, bodyKeys(newSnake, false));
if (space < Math.ceil(newSnake.length * spaceFactor)) return false;   // spaceFactor 默认 1.0
```

**⚠️ 我做过参数扫描**：把 `spaceFactor` 从 1.0 调到 1.5，达标率**完全没变**（都是 299/300）。
这个"参数不敏感"的结果本身有价值——它排除了"靠调参碰运气"的嫌疑，
说明剩下的那一局失败不是"不够保守"造成的，而是保命模式下的一步误判。

**洪水填充也要用 BFS 而不是递归 DFS**：400 格用递归有爆栈风险，而且 JS 引擎对深递归不友好。

### 第三层：三级降级策略

```js
① 食物可达 → 沿 BFS 最短路走第一步（且这一步必须通过安全性校验）
② 最短路第一步不安全 / 食物不可达 → 追自己的尾巴（沿着 BFS 到尾巴的路径走），先活下去
③ 连尾巴都追不到 → 在所有合法方向里选"走完之后活动空间最大"的那个
④ 全都不行 → 随便走一个合法方向（几乎不会发生）
```

代码里用 `state.aiLost` 标记"当前处于保命状态"，界面上会显示
「AI 暂时吃不到食物，正在追尾保命…」。**这个标记很重要**：它把 AI 的内部决策暴露给用户，
看到这个提示就知道它不是在乱走，而是在主动放弃追食物、优先活命。

**实测：整个 300 局里，"保命状态"的步数占 9.1%。** 也就是说 AI 有将近一成的步数
在主动放弃追食物、优先活命——这正是它比贪心策略强的原因。

### 可视化：把搜索路径画出来

`state.aiPath` 保存了最近一次规划出的路径（从蛇头到目标的坐标序列），绘制时用虚线画出来：

```js
ctx.setLineDash([4, 4]);
ctx.beginPath();
ctx.moveTo(蛇头中心);
g.aiPath.forEach(c => ctx.lineTo(c.x*CELL + CELL/2, c.y*CELL + CELL/2));
ctx.stroke();
```

**这不只是好看。** 从画面上能直接读出 AI 当前的决策：
- 橙色虚线指向食物 → AI 正常追击中；
- 橙色虚线拐向蛇尾 → AI 正在保命；
- 没有虚线 → AI 处于降级策略。

把算法的内部状态画出来，比只在文字里说"它用 BFS 找路"直观得多。

## 1.6 性能：为什么 AI 计算不会卡住画面

| 操作 | 规模 | 耗时量级 |
|---|---|---|
| 一次 BFS | 最多 400 格，每格 4 个邻居 | 微秒级 |
| 一次洪水填充 | 最多 400 格 | 微秒级 |
| 一次决策（含最多 4 次安全性校验） | 相当于约 8 次 400 格遍历 | **约 0.15 ms** |

而游戏每 150ms 才走一步，**AI 占用不到千分之一的时间**。所以完全不需要
Web Worker 或增量计算这类复杂方案。**性能优化要基于测量，不是基于直觉。**

## 1.7 几个设计取舍

**为什么不用 A\* 算法？** A\* 在 BFS 基础上加了启发式估价函数，适合"大地图、障碍多"的场景。
这里棋盘只有 400 格、目标是单个格子、每步代价都是 1，BFS 已经最优且足够快，
加启发式只会增加复杂度而不带来可测量的收益。如果棋盘扩到 200×200 我会考虑 A\*。

**为什么不用哈密顿回路（可以保证通关）？** 沿固定回路走确实能 100% 不撞到自己，
但代价是效率极低——蛇要绕很远才能吃到食物，画面很难看，演示效果差；
而且写死一条回路等于把寻路问题绕过去了，失去了展示算法的意义。
我选择"最短路径 + 安全性校验"，用 99.7% 的达标率换取 65+ 的平均得分和更聪明的观感。

**`spaceFactor` 为什么取 1.0？** 因为扫描 1.0 / 1.15 / 1.3 / 1.5 / 2.0 五档，
达标率完全一样（都是 299/300），而阈值越小平均得分越高（65.6 对 60.7）。
这是用数据做的决定，不是拍的。

**为什么两套 AI 都留着？** 用来对比。可以在同一界面切换，看到朴素贪心平均吃 30 个左右、
而 BFS 版能吃 65 个以上。**能演示出"改进前 vs 改进后"的差异，比只说"我优化了算法"更有说服力。**

# 第二部分 · 电路原理

## 2.1 RC 低通滤波

### 时间常数 τ 是怎么来的

电容的电流与电压关系是 `i = C·du/dt`，电阻上是 `v_R = iR`。对 RC 串联电路用基尔霍夫电压定律：

```
v_in = v_R + v_out = R·C·(dv_out/dt) + v_out
```

这是一个一阶线性微分方程，整理成标准形式：

```
τ · dv_out/dt + v_out = v_in ,   其中 τ = RC
```

解出来，输出对输入的响应是：

```
v_out(t) = v_final - (v_final - v_start)·e^(-t/τ)
```

**τ 的物理意义：电压走完"从起点到终点"这段距离的 63.2% 所需的时间。**
代入 `t = τ` 得 `e⁻¹ ≈ 0.368`，即还剩 36.8%，所以走完了 63.2%。三个常用点：

| 时间 | 已完成比例 | 剩余 |
|---|---|---|
| τ | 63.2% | 36.8% |
| 2τ | 86.5% | 13.5% |
| 3τ | 95.0% | 5.0% |
| 5τ | 99.3% | 0.7%（工程上认为"充满"） |

**这就是我"从波形上实测 τ"的依据**：找到跳变后的终值和起点，取达到
`v_start + (v_final - v_start)×0.632` 的时刻，减去跳变时刻，就是实测 τ。

**本次参数**：R = 1kΩ，C = 1μF → **τ = RC = 1 ms**。

### 截止频率 fc 是怎么来的

对电容用复阻抗 `Z_C = 1/(jωC)`，RC 分压（输出取自电容两端）：

```
H(jω) = (1/(jωC)) / (R + 1/(jωC)) = 1 / (1 + jωRC)
```

模长：

```
|H| = 1 / √(1 + (ωRC)²) = 1 / √(1 + (2πfRC)²)
```

**⚠️ 为什么截止频率定义在 `|H| = 1/√2 ≈ 0.707` 处，而不是 0.5 处？**

因为功率正比于电压平方。`|H| = 1/√2` 时，`|H|² = 1/2`，**功率正好降到一半**，
换算成分贝就是 `20·log₁₀(0.707) = -3.01 dB`。所以"截止频率"又叫 **-3dB 频率**。

令 `2πfRC = 1` 即得：

```
fc = 1/(2πRC) = 1/(2π × 1000 × 1e-6) ≈ 159.155 Hz
```

**相频特性**：`∠H = -arctan(2πfRC)`。在 `f = fc` 时 `2πfRC = 1`，
所以 **`∠H(fc) = -arctan(1) = -45°`**。这就是我在波特图里标注 -45° 的原因。

低频（f ≪ fc）：`|H| ≈ 1`（不衰减，相位 ≈ 0°）；
高频（f ≫ fc）：`|H| ≈ 1/(2πfRC)`，频率每升高 10 倍幅值降 10 倍，即 **-20 dB/十倍频**，
相位趋近 -90°。**这两个渐近线特征是判断"一阶低通"的标志。**

### 为什么要做方波瞬态分析（这是本轮补的东西）

**⚠️ 这是我最开始没想明白的点**：既然已经做了交流扫描（AC）得到幅频特性，
为什么题目还要专门做方波瞬态？

关键在**傅里叶级数**：一个方波可以分解成基波加上无穷多个奇次谐波：

```
方波 = (4/π) · [sin(ωt) + (1/3)sin(3ωt) + (1/5)sin(5ωt) + ...]
```

所以给低通滤波器输入方波，实际上相当于**同时给基波和各次谐波做了不同的衰减和相移**：

- **高次谐波被滤掉** → 方波的陡峭边沿变得圆滑（这就是"低通"的直观体现）；
- **基波被保留** → 波形主体还在。

**瞬态响应和频域响应描述的是同一个系统的同一件事**，只是一个从时域看、一个从频域看。
题目要求两个都做，就是要我建立这个对应关系：

| 现象 | 频域解释 |
|---|---|
| 上升沿不是垂直的，而是按指数规律爬升 | 边沿的陡峭度由高次谐波决定，高频被衰减 |
| 上升沿花的时间约 2.2τ 到 95% | 带宽不足，高频分量丢失 |
| 方波变成"馒头形"（三角化） | 当方波频率远高于 fc 时，只剩基波通过 |

我选的方波频率是 **200Hz**（周期 5ms），而 fc ≈ 159Hz：方波频率略高于 fc，
半周期 2.5ms ≈ 2.5τ，**正好能清楚看到电容充电爬升的过程**，又不会慢到看不出滤波效果。

**⚠️ 另一个坑**：`plt.rcParams['font.sans-serif'] = ['SimHei']` 必须设置，
否则 matplotlib 的中文标签会显示成方块（tofu）。还要配
`plt.rcParams['axes.unicode_minus'] = False`，否则负号也会变成方块。

### 误差表为什么会"看起来全是 0.00%"

原表格用 `f"{err:5.2f}%"` 打印，保留 2 位小数。在 100kHz 处，理论值 0.00159 V、
仿真值 0.0016 V，**绝对差只有 1e-5 V**，相对误差约 1%，但它是 `0.0106...` 这种量级吗？
不是——我实际算过，最大相对偏差 **1.067%**，四舍五入后应该显示 `1.07%`。

**那为什么原来显示 0.00%？** 因为仿真的电压值和理论值在这个频点的**有效数字不足**：
仿真输出在 0.0016 V 这个量级上，两位小数的打印精度已经吃掉了差异。
换句话说：**不是误差真的为 0，是打印精度不够，看起来像 0。**

**修正方式**：误差列改成保留 3 位小数，并在表下加注说明。
**这一条我在整改说明里专门写了**，因为"用一个误导性的 0.00% 让表格看起来完美"
是不诚实的做法，哪怕不是故意的。

## 2.2 戴维南定理验证

### 定理本身

**任何由线性电阻和独立源组成的含源二端网络，对外都可以等效成一个电压源 V_th 串联一个电阻 R_th。**

- `V_th` = 端口**开路**时的电压（V_oc）
- `R_th` = 把网络内所有**独立源置零**（电压源短路、电流源开路）后，从端口看进去的等效电阻

我的电路：5V 电源 + R1=1kΩ 串联 + R2=2kΩ 对地，输出取自 R2 两端。

```
V_th = 5 × R2/(R1+R2) = 5 × 2/3 ≈ 3.3333 V
R_th = R1 ∥ R2 = (1×2)/(1+2) = 2/3 kΩ ≈ 666.6667 Ω
```

### ⚠️ 为什么必须做两次仿真（V_oc 和 I_sc）

**这是本轮补的第一个缺口。** 定理的验证要**两个端点都能吻合**才算完整：

1. **开路**：端口不接负载，`V_oc` 应该等于 `V_th`；
2. **短路**：端口直接短路，`I_sc` 应该等于 `V_th / R_th`。

因为一条直线由两点确定：`V_oc` 给出纵轴截距，`I_sc` 给出横轴截距，
两者确定了这条**负载线**（外特性曲线），等效才是完整的。

而且 `R_th = V_oc / I_sc` 提供了一个**独立的求 R_th 的方法**——
不用"把电源置零再算电阻"，而是用两次实测值算出来。这是一个很好的交叉验证。

**我的数值**：`V_th ≈ 3.3333 V`，`R_th ≈ 666.67 Ω`，所以
`I_sc = V_th/R_th ≈ 5.000 mA`。

**⚠️ 仿真里怎么测电流**：SPICE 里"电流表"不好直接放，标准做法是**在支路里串一个 0V 电压源**，
然后读这个电压源的电流。因为它是 0V，不会影响电路工作点，但会给仿真器一个"可读电流的支路"。
短路电流就是把输出端口用这样一个 0V 源直接接地。

### 为什么接负载后的电压验证是不够的

原来的表格只对比了"接不同负载时原电路和等效电路的输出电压"。**电压一致只是必要条件。**
正确的做法是同时对比**电压和电流**：

```
I_L = V_o / R_L
```

如果两个电路的 `V_o` 和 `I_L` 在多个负载点都吻合，才能说明它们在端口上**完全等效**。
而且电流能暴露一些电压看不出来的问题（比如接小负载时的带载能力）。

**⚠️ 一个有意思的观察**：`R_th = 2/3 kΩ = 666.667 Ω`，但我脚本里写的是
`Rth = 2/3 * 1e3`——注意这个表达式在 Python 里是 `(2/3)*1000 = 666.666...`，
而不是 `2/(3*1000)`。**运算符优先级/结合性在这里很容易写错**，
如果我写成 `2/3*1e3` 是对的，写成 `2/(3*1e3)` 就变成了 0.000667 Ω，整个电路就错了。
我复核过：原来脚本写的是 `2/3 * 1e3`，**是对的**。

## 2.3 NMOS 共源放大电路（本轮最重要的修正）

### 手算静态工作点

**第一步：栅极电压。** 栅极电流为零（MOS 输入阻抗极高），所以 Rg1 和 Rg2 就是纯分压：

```
V_G = VDD × Rg2/(Rg1+Rg2) = 5 × 40/(60+40) = 2 V
```

源极接地，所以 `V_GS = V_G - 0 = 2 V`。

**第二步：漏极电流。** 先假设工作在饱和区，用饱和区平方律：

```
I_D = (K/2)(V_GS - V_th)² = (0.8m/2)(2-1)² = 0.4 mA
```

**⚠️ 注意 `K` 的量纲**：题目给 `K = 0.8 mA/V²`，而 SPICE 的 `KP` 参数就是这个 K。
公式里是 `K/2`，所以是 `0.4 mA`。**很多人会把 K 和 K/2 搞混**，
或者误以为 K 就是 SPICE 里的 β。我在脚本里写的是 `K/2 * (V_GS-Vth)**2`，与公式一致。

**第三步：漏源电压。**

```
V_DS = VDD - I_D·R_D = 5 - 0.4m × 2k = 5 - 0.8 = 4.2 V
```

**第四步：饱和区判断（必须做，这是假设能否成立的自检）。**

```
饱和区条件：V_DS > V_GS - V_th
          4.2 V > 2 - 1 = 1 V   ✅ 成立
```

所以假设自洽，管子确实在饱和区，可以当放大器用。

> **⚠️ 这里有个重要的思维方式**：饱和区判断不只是"检查一下"，
> 它是**假设自洽性的验证**。如果算出 `V_DS < V_GS - V_th`，说明假设错了，
> 管子在线性区，必须换线性区公式重算。**先假设、再代入、最后自检**，这是解这类题的标准流程。

### ⚠️ 本轮的核心修正：漏掉 λ 项导致 8% 的假误差

**我原来的手算（错的）：**

```
I_D = (K/2)(V_GS - V_th)² = 0.4 mA          ← 少了 (1+λV_DS)
V_DS = VDD - I_D·R_D = 4.2 V
```

**SPICE Level 1（Shichman-Hodges）模型的真实方程：**

```
I_D = (K/2)(V_GS - V_th)² · (1 + λ·V_DS)      （饱和区）
```

**λ 是沟道长度调制系数。** 物理上，当 `V_DS` 增大时，漏端的耗尽层变宽，
有效沟道长度 `L` 变短；而 `I_D ∝ 1/L`，所以电流**随 V_DS 缓慢上升**，
表现为输出特性曲线在饱和区不是水平的，而是略微上翘。λ 就是这个上翘的斜率。

**为什么这个方程必须联立求解？** 因为 `I_D` 出现在 `V_DS` 的表达式里，
而 `V_DS` 又反过来影响 `I_D`：

```
I_D  = (K/2)(V_GS-V_th)²(1 + λ·V_DS)     ┐
                                          ├─ 两个方程，两个未知数
V_DS = VDD - I_D·R_D                      ┘
```

代入消元会得到一元二次方程，也可以**迭代**：

```python
ID = K/2*(VGS-Vth)**2          # 先给初值（忽略 λ）
for _ in range(20):
    VDS = VDD - ID*Rd
    ID  = K/2*(VGS-Vth)**2 * (1 + lam*VDS)
```

我实际迭代的结果：

| 量 | 漏 λ 的简化手算 | 含 λ 的自洽解 | 仿真值 | 自洽解误差 |
|---|---|---|---|---|
| I_D | 0.4000 mA | **0.4331 mA** | （仿真内部量） | — |
| V_DS | 4.2000 V | **4.1339 V** | **4.1339 V** | **0.00%** |
| gm | 0.8000 mS | **0.8661 mS** | 见表格 | — |
| r_o | 125 kΩ | 115.5 kΩ | — | — |
| A_v | -1.5748 | **-1.7028** | **-1.7050** | **0.13%** |

**结论：那 8% 的"误差"完全来自手算漏掉的一项，不是"SPICE 模型更完整"。**
（这个结论我验算过：把 λ 代回去自洽求解，V_DS = 4.1339 V 与仿真完全一致。）
补上 λ 之后，直流工作点与仿真**完全吻合**，增益误差降到 0.13%。

**⚠️ 这里必须搞清楚的逻辑**：SPICE Level 1 用的**就是课本上那条平方律公式**，
它并没有"额外包含更完整的效应"。我当初之所以会接受"模型更完整"这个说法，
是因为我没有回到公式本身去核对，而是把误差**归因给了一个不可验证的模糊原因**。
**这是这次整改里对我触动最大的一点：误差是线索，不是结论。**

### 小信号参数

> **⚠️ 先把 K 和 gm 分清楚，这两个最容易被当成同一个东西。**
>
> | 量 | 是什么 | 谁给的 | 本电路的值 |
> |---|---|---|---|
> | **K** | 跨导参数，描述器件本身"多能导电" | **题目给定** | 0.8 mA/V² |
> | **gm** | 跨导，描述**在这个工作点上**栅压对漏流的控制能力 | **要自己算** | 0.8661 mS |
>
> 两者量纲相同（都是 A/V），所以数值看起来像"同一个东西"，但物理含义完全不同：
> **K 是工艺参数、gm 是工作点参数**。gm 依赖 V_GS 和 V_DS，换个偏置点 K 不变而 gm 会变。
> 常见错误是直接把 K 的值当成 gm 填进小信号模型——**这样算出来的增益会差 8%**。

**跨导 gm**：`gm = ∂I_D/∂V_GS`，物理意义是"栅压变化 1V 能让漏电流变化多少"。

从含 λ 的公式求偏导（注意 `V_DS` 也随 `I_D` 变，严格说要用全微分，工程上近似取：

```
gm = K·(V_GS - V_th)·(1 + λ·V_DS)
   = 0.8m × (2-1) × (1 + 0.02×4.1339)
   = 0.8m × 1.0827 ≈ 0.8661 mS
```

**注意这里 `K = 0.8 mA/V²` 是题目给的参数，而算出来的 `gm ≈ 0.8661 mS` 才是跨导。**
如果偷懒直接用 K 的值（0.8 mS）当 gm，就会得到偏小 8% 的增益——这正是最初那 8%
误差的一部分来源。

**输出电阻 r_o**：λ 的倒数关系

```
r_o = 1/(λ·I_D) = 1/(0.02 × 0.4331m) ≈ 115.5 kΩ
```

> **⚠️ 直观理解 `r_o = 1/(λI_D)`**：λ 越大，输出特性曲线越"上翘"，
> 说明管子越像一个不理想的电流源、等效内阻越小。所以 `r_o ∝ 1/λ`，符合直觉。

**为什么 gm 要"实测"**：手算的 gm 是按公式算的，实测的 gm 是
`ΔI_D/ΔV_GS`（数值微分，栅压微扰 ±1mV 取中心差分）。
两者对比才能说明"我的小信号模型是否靠谱"。
**这是本轮补的第三个缺口**（原来表格里 gm 只有手算值）。

### 增益与"反相"

**漏极看进去的总电阻**是 R_D 和 r_o 的并联：

```
R_out = R_D ∥ r_o = (2 × 115.5)/(2 + 115.5) ≈ 1.9685 kΩ
```

**增益：**

```
A_v = -gm · R_out ≈ -0.8661m × 1.9685k ≈ -1.705
```

**⚠️ 那个负号就是"反相"，它的来源是：**

共源级的输入在**栅极**，输出在**漏极**。栅压升高 → `V_GS` 增大 → 漏电流增大 →
**R_D 上的压降增大** → 漏极电压**降低**。

**输入升、输出降** —— 这就是 180° 相位差。所以：

- 数学上：`A_v = -gm·R_out`，负号来自"漏极电流增大导致漏极电压下降"这个反向关系；
- 波形上：输入正弦的峰值时刻，正好是输出正弦的谷值时刻，两者错开**半个周期**。

**我原来的失误**：`nmos_calc.pdf` 里我写对了（`Av = -1.57`，还注明"输出与输入反相"），
但 README 和表格里写成了 `1.5748`、`1.7050`——**把负号丢了**。
而任务书电路③明确要求"输入/输出波形图（**反相放大**）"。
更糟的是瞬态图里我做了 `v_out - mean(v_out)` 减掉直流分量，
两条曲线都对称于 0，**图里看不出任何相位关系**。

**修正**：增益统一保留负号；瞬态图改成上下两图——
上图用**真实电压**（输出在 4.13V 附近摆动），直观看到输出直流工作点；
下图用**放大后的交流分量**，并在输入峰值和输出谷值之间画竖虚线，**直接显示相差 180°**。

### 为什么实测增益（1.705）和自洽手算（1.7028）还差一点点

差 0.13%，来源有几个小的二阶效应：

1. **体效应（Body Effect）**：衬底与源极都接地，`V_BS = 0`，这一项在本电路里没有贡献；
2. **gm 的全微分修正**：严格求 `gm` 时 `V_DS` 随 `V_GS` 变化，我用了近似；
3. **瞬态测量的离散误差**：增益是用峰值差除峰值差算的，采样点未必正好落在峰值上。

**0.13% 这个量级已经属于"数值误差"而不是"模型误差"了。**
把这三个来源讲清楚，比笼统地说"模型更完整"有说服力得多。

# 第三部分 · 前端与工程

## 3.1 `localStorage` 存数据

**是什么**：浏览器提供的键值存储，**只能存字符串**，容量约 5MB，**关闭浏览器后仍然保留**
（这是它能做"刷新后保留主题/最高分"的原因）。

**⚠️ 三个坑**：

1. **只能存字符串**。存数字要 `String(n)`，读出来要 `parseInt(raw, 10)`。
   **一定写第二个参数 10**，否则 `"08"` 这类字符串会被按八进制解析（老引擎行为）。
2. **复杂数据要序列化**：战绩列表是数组，用 `JSON.stringify` / `JSON.parse`。
   **`JSON.parse` 必须包在 try/catch 里**——如果存储里的数据被手动改坏或版本不兼容，
   不捕获就会让整个脚本挂掉。
3. **隐私模式下可能抛异常**。所以我的 `write()` 里包了 try/catch，写失败就静默跳过，
   不影响游戏本身能玩。

**键名设计**：我用 `snake.highScore` / `snake.gamesPlayed` / `snake.history` / `snake.theme`
这种带命名空间前缀的形式，避免和同域下其他页面的键冲突。

## 3.2 主题切换：CSS 变量

```css
:root[data-theme="light"] { --bg:#eef3f9; --text:#12263a; --snake-head:#1b7f4d; ... }
:root[data-theme="dark"]  { --bg:#0d1420; --text:#e8eef7; --snake-head:#38d08a; ... }
```

然后所有样式都引用变量：`background: var(--panel)`。

切换时只要改一个属性：

```js
document.documentElement.setAttribute('data-theme', 'dark');
```

**为什么这样比"逐个元素改颜色"好**：

- 只改**一个**属性就能整站换肤，不会漏掉任何元素；
- 颜色集中定义，加第三套主题（比如护眼绿）只要再加一块变量；
- **Canvas 也能吃到这套变量**：`getComputedStyle(document.documentElement).getPropertyValue('--snake-head')`
  就能把 CSS 颜色读进 JS，传给 `ctx.fillStyle`。**这样界面和画布的颜色永远一致**，
  不会出现"改了主题但蛇还是旧颜色"的 bug。

**⚠️ Canvas 颜色读取的性能**：`getComputedStyle` 有一定开销，我在 `draw()` 里读一次
并缓存到局部变量（每帧一次可以接受；如果每画一个蛇身格子都读一次就浪费了）。

## 3.3 状态机

我用一个 `status` 字段表示游戏所处阶段：

```
ready ──开始──▶ running ──死亡/通关──▶ over / win
                   │  ▲
              暂停 ▼  │ 继续
                  paused
```

**为什么要显式状态机**：如果只用 `gameOver` 一个布尔值，就分不清
"还没开始"、"正在玩"、"暂停中"、"已结束"这四种情况——
比如"还没开始"和"暂停中"都需要"按方向键就继续"，但"已结束"应该重开一局。
**布尔值不够表达，就需要状态机。**

## 3.4 存储层与界面层分离

`snake_store.js` 只负责"怎么存、怎么读"，`snake.html` 只负责"显示成什么样"。
好处：

- **可测试**：`createStore(storage)` 接受任意 storage 对象，测试时可以塞一个内存版的假
  localStorage 进去，不需要真的开浏览器；
- **可替换**：如果以后要改成存到服务器（多设备同步），只改这一层，界面完全不用动。

**⚠️ 一个关键细节**：`snake_store.js` 里我用
`const auto = (typeof localStorage !== 'undefined') ? createStore(localStorage) : null;`
做环境判断。因为 Node 里没有 `localStorage`，如果不判断，测试脚本 `require` 这个文件就会报错。
